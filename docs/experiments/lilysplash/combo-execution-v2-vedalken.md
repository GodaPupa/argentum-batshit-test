# Lilysplash Mentor Combo-Execution v2 — Vedalken Entrancer

Companion to [combo-execution-v1.md](combo-execution-v1.md), which proved the AI autonomously executes the
deck's original mill combo (Peregrine Drake + Ghostly Flicker + Archaeomancer + Sage's Row Denizen). This
is the specific follow-up `challenger-wincon-v1.md`'s own Verdict section named and called out of scope:
"a scenario test that actually assembles infinite mana with only Vedalken Entrancer and an untapper on
board (no Peregrine Drake/Archaeomancer/Ghostly Flicker loop at all) and checks that the opponent decks
out."

**Result: the AI does not execute this line correctly.** It repeatedly mills *itself* instead of the
opponent and decks out first. This traces to a real, reproducible engine/AI bug, not a Lilysplash-deck
issue, and not a "the AI just doesn't find the combo" story like a stall would be — it actively finds and
loops the combo, aimed at the wrong player, every time.

## Method

`LilysplashVedalkenComboExecutionTest.kt` (`ai/src/test/kotlin/com/wingedsheep/ai/engine/`), same pattern
as the companion test: a `ScenarioTestBase` board with Vedalken Entrancer on the battlefield and Freed
from the Real already attached to it (`withCardAttachedTo`), funded with 24 untapped Islands (this loop
isn't mana-positive on its own — 2 mana spent per 2 cards milled — so unlike the Peregrine Drake loop it
needs the mana provided directly rather than generated by the loop itself), opponent life set to
1,000,000 to remove combat as a competing outcome, opponent given a 20-card filler library. Driven by the
real `AIPlayer` (`AiProfile.PRODUCTION_CANDIDATE_EXPIRING`) on both seats, same step/stall-budget loop as
the companion test.

## What actually happened

Traced via temporary per-step library logging (both players), confirmed identically on two different RNG
seeds (`20260916L`, `20260917L`) — ruling out shuffle-order luck, since a 20/40-card library of identical
filler cards ("Forest") gives the shuffle nothing to vary anyway:

- For roughly a dozen turns, nothing happens except each player's own normal draw step. The AI does not
  even attempt the combo yet.
- The AI then activates the Vedalken Entrancer + Freed from the Real loop repeatedly during a combat
  step (`DECLARE_BLOCKERS`, where it still holds priority) — but every single mill lands on **its own
  library**, not the opponent's. Across the full run, the opponent's library barely moves (only from
  its own natural draws); the pilot's library drains from 40 to 0 entirely from self-inflicted mills.
- The game ends with the AI decking itself out and losing (`winnerId` = the opponent) — the opposite of
  the intended outcome, and for a different reason than simply losing the race.

## Root cause

Traced by reading the actual code (not assumed), two compounding gaps, both generic — neither is specific
to Vedalken Entrancer or to mill effects:

1. **`TargetSelection.kt`'s player-target heuristic can never prefer the opponent.**
   `ai/src/main/kotlin/com/wingedsheep/ai/engine/TargetSelection.kt` (`rank()`, ~lines 48-59) scores a
   `Targets.Player` candidate by checking `projected.getController(entityId)` and comparing it against
   the acting player. But `getController` is only populated for battlefield entities — `StateProjector`
   never creates a projection entry for a *player* entity — so for a player-target candidate,
   `controller` is always `null`, `isOpponent` is always `false`, and both the ability's own controller
   and the real opponent score the identical `-5.0`. The `5.0`-for-opponent branch can never fire for
   any `Targets.Player` effect: mill, life loss, discard, "target player draws a card," all of it.
2. **The production evaluator has no library-size awareness.** `AiProfile.PRODUCTION_CANDIDATE_EXPIRING`
   resolves to `EvaluationWeights`'s 5-feature composite (life, boardPresence, cardAdvantage,
   threatAssessment, tempo) — none of which read library size, so simulating "mill self" and "mill
   opponent" scores identically there too. A separate library-aware feature
   (`librarySizeDifference` in the Phase 9 "raw" evaluator) exists in the codebase but is dormant for
   this profile (`raw-eval-weights.json` is an empty object, so nothing routes to it).
3. With both the heuristic and the evaluator tied, `Strategist.chooseCommittedTargets`'s
   `maxByOrNull` calls resolve every tie by picking whichever candidate the engine's target enumerator
   happens to list first. Empirically, that is the ability's own controller — a static tie-break, not
   randomness, which is exactly why two different RNG seeds produced identical behavior.
4. No card-specific advisor exists for Vedalken Entrancer or for mill effects in general
   (`CardAdvisorRegistry`'s modules cover only Bloomburrow and Onslaught), so nothing overrides the
   broken generic path for this card.

## Scope of the finding

This is a **broad** AI/engine gap, not a narrow one about this one card: any `Targets.Player` effect with
no other differentiating signal available to the evaluator will tie-break the same way. Vedalken Entrancer
just happens to be the card that makes the gap *fatal* rather than cosmetic — a repeatable activated
ability with no other use for the mana, so the AI leans on it every priority window it can, always aimed
at itself.

Fixing this is `add-feature` territory (per this repo's own routing rules) — it means changing shared AI
target-ranking and/or evaluator code that every `Targets.Player` effect depends on, with its own testing
surface well beyond this deck experiment. It is out of scope for this experiment to fix, and doing so here
would blur which change caused which effect.

## Test status

`LilysplashVedalkenComboExecutionTest` is committed and runs as part of the normal `:ai:test` suite
(passing), but it **pins today's actual behavior** rather than the originally-intended one — the same
`KNOWN_FAILURES` philosophy `PuzzleSuiteTest` uses for tracked AI limitations: the assertion checks that
the pilot decks itself out and loses, not that the opponent does. This keeps CI green without hiding the
bug, and the test's own doc comment says explicitly: if this assertion ever starts failing, check whether
the underlying `TargetSelection.kt`/evaluator gap got fixed before assuming a regression, and if so,
rewrite the test to assert the intended outcome (opponent's library reaches 0) instead.

CI: `lilysplash-preflight.yml` job `combo-execution` now runs both combo-execution tests together via
`just test-class 'Lilysplash*ComboExecutionTest'` on every push to `lilysplash/lab` that touches either
test file. CI run `019a191022`, `Lilysplash Preflight #14`,
<https://github.com/GodaPupa/argentum-batshit-test/actions/runs/35007294955>, 6m23s, both jobs
(`final-optimized`, `combo-execution`) green — a green `combo-execution` job confirms this test's pinned
(buggy) assertion holds, not that the Vedalken line works.

## Verdict

**The Vedalken Entrancer win condition, as currently implemented in the AI, does not work in AI-vs-AI
play.** This is unrelated to anything about the Lilysplash deck itself or to Stage 4's card choices — it
is a genuine, reproducible bug in the AI's generic target-selection and evaluation code for any
player-targeted effect, discovered because this specific card's repeatable activated ability makes the
bug's consequences catastrophic instead of incidental. The deck's actual win condition in practice remains
the original combo validated in `combo-execution-v1.md`; Vedalken Entrancer should not be relied on as a
working alternate win condition against the current AI until this is fixed at the engine/AI level.
