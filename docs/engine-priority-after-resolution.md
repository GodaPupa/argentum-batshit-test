# Priority after stack resolution

## Verified defect and rules boundary

Pest postboard support batch A's rejected candidate
`28b7cb4dd5b39bbd88409878a0f5ec8ea08c3579` exposed this shared engine defect. In
[validation run 36086800652](https://github.com/GodaPupa/argentum-batshit-test/actions/runs/36086800652),
an opposing Lightning Bolt resolved and the active player's subsequent Divination was rejected
with `You don't have priority`. The retained archive is artifact `10844627205`, ZIP SHA-256
`ba8388b78271aa9132478a3fd0835dfe4710c85866d2f4b54f540faf2113d141`.

Source inspection identified two causes. `PassPriorityHandler.resolveTopOfStack` explicitly
returned priority to the resolved spell or ability's controller. After a paused resolution,
`SubmitDecisionHandler` instead returned priority to the player who answered the last decision.
Both can differ from the active player.

The [official Comprehensive Rules](https://magic.wizards.com/en/rules), effective 2026-09-25,
distinguish these boundaries. Rule 117.3b gives the active player priority after a non-mana spell
or ability resolves. Rule 117.3c lets an acting player retain priority after casting, activating,
or taking a special action. Rule 117.5 requires state-based actions and trigger placement to
finish before that priority window opens. Rule 117.4 requires every remaining player to pass in
succession before the next resolution or step advance. The exact official text URL, byte length,
and SHA-256 are bound in `engine-priority-after-resolution-sources.json`; the dedicated workflow
retrieves and retains those bytes and refuses a digest mismatch or a future-effective source.

## Canonical repair

The prospective implementation base is accepted main
`c6953354b1b799fe4506eb9e44ff25523a132d8e`. This is one shared engine repair, with no card,
SDK, deck, pilot, sample-plan, seed, or official-execution changes.

`GameState.stackResolutionPendingPriority` records that a stack resolution has started and is
still awaiting its next priority window. `PassPriorityHandler` establishes this boundary before
resolution. It survives effect choices, state-based-action choices, and target choices for
triggered abilities generated during resolution. Completion restores priority to the current
active player through the existing departed-player redirect, clears the passed-player set, and
emits the existing `PriorityChangedEvent`.

`SubmitDecisionHandler` consults this explicit boundary when the complete continuation chain
finishes. It does not infer the recipient from the answerer or from whether other spells remain
on the stack. Cast-time modal choices and ordinary activation choices outside a resolution keep
their existing actor-retains behavior. End-of-turn and game-over paths clear the boundary; the
existing policy that abandons a departed player's unanswerable decision also clears it.

A cast-time prompt encountered inside a resolution can complete while its outer effect tail and
spell finalizer remain. The decision handler drains that automatic work while the marker is set;
pauses and errors still propagate. It preserves each event batch's processed-trigger provenance so
the cast's already detected triggers are not duplicated and a new tail's triggers are not lost.
Ordinary cleanup or untap choice completion advances the step only outside a marked resolution.
The existing cleanup-discard regression also runs unchanged.

The marker is serialized when true. Its false default is explicitly omitted even with
`encodeDefaults=true`, so ordinary historical snapshot bytes do not gain a default field. This
does not translate old sampled evidence to a new engine or silently migrate a frozen experiment.
Existing legacy snapshot and continuation trace tests run unchanged. No golden or accepted
historical result is regenerated by this change.

## Qualification

Seventeen focused engine cases exercise actual public actions and decisions:

- Opposing Bolt resolves, then the active player can immediately cast Divination.
- An opposing activated response resolves with another spell still on the stack.
- A nonactive controller chooses a resolution-generated trigger's target, then the active player
  receives priority before that trigger resolves.
- An opponent's discard choice survives an exact state serialization round trip.
- An opposing legend-rule choice completes before the active player's priority window.
- Four-player unless-pay choices cover decline and payment, including a second mana-source
  decision with active, countering, and answering players all distinct.
- A four-player cast-time modal prompt retains the nonactive caster's priority.
- A cleanup-window legend choice keeps another spell on the stack and restores active priority.
- Nested modal free casting, including cancellation, drains the outer tail before priority; separate
  cast and life-gain observers verify no duplicate cast trigger and no lost outer-tail trigger.
- A departed active player is skipped; a departed decision owner cannot strand the boundary.
- End-of-turn and terminal resolution clear the marker.
- False marker omission is verified with defaults enabled.
- A malformed imported stack is rejected without publishing the marker, changing the state,
  or emitting events; no synthetic result is assigned.

The dedicated workflow also runs existing stack-war, continuation, legend-rule, leave-game,
shared-team priority, conditional-flash, legacy trace and legacy serialization tests. Each of its
ten stages preserves XML before the next test invocation, including failures. General CI remains
required. There is no blanket test waiver, golden update mode, or official gameplay path. A failed
existing expectation must be inspected against its actual rules and trace before any correction.

The local environment has no approved Kotlin build runtime. Static review and file identity
checks prepare the change; compilation, behavioral results, and the retained artifact audit are
required for acceptance. The existing server and client already consume the priority state and
event, so no new prompt, DTO or UI control is introduced.

## Experimental consequences

This repair changes available response windows and therefore may change pilots' actions and
eventual outcomes. A green regression gate cannot validate prior experimental results against
the repaired engine. Each project must assess historical evidence under its own invalidation
rules and qualify integration prospectively before freezing a successor block. Shared source
does not make evidence or execution authority interchangeable.

The Monster one-shot's frozen source remains immutable; this PR cannot execute or replace its
four assignments. No official seed is generated, game initialized, action submitted or outcome
exposed by this gate. Its only gameplay consists of deterministic regression fixtures.
